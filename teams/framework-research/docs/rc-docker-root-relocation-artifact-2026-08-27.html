1 Current situation — measured, not assumed

Disk layout

Single NVMe disk, LVM on top. Two logical volumes matter, both ext4:

/var/lib/docker is a plain directory on the root LV — not a separate mount, not a symlink, no bind-mount tricks in /etc/fstab. findmnt shows exactly two real mount points, / and /home.

Docker configuration

  • Storage driver: overlayfs via the containerd snapshotter (io.containerd.snapshotter.v1) — not the classic overlay2 graphdriver. This turns out to matter a great deal; see the catch below.
  • Docker Root Dir: /var/lib/docker — no data-root override set. /etc/docker/daemon.json does not exist. No docker.service.d/ drop-ins.
  • Live Restore: disabled. Stopping docker.service stops every running container.

A clean, unmodified default install. Nothing has been relocated before.

The catch — found in review, would have silently defeated the plan

containerd is a separate daemon with its own storage root, and that is where most of the bytes live. On this host containerd is the system containerd.io package running as its own enabled systemd unit (PID 1367, up 3 weeks, one containerd-shim-runc-v2 per container). docker.service is merely a client of it (Wants=/After=containerd.service). Its config, /etc/containerd/config.toml, has #root = "/var/lib/containerd" commented out, so it runs on that default.

With the snapshotter driver, image layers and container writable layers belong to containerd, under /var/lib/containerd — a measured 21 G of the 43 G total (the other 22 G is Docker's own tree, fattened by container logs). Docker's own data-root holds volumes, network config and metadata.

So the obvious fix — set data-root in daemon.json, move /var/lib/docker — would complete cleanly, pass every Docker-level check, show the new path in docker info, and leave root at roughly 55%. Asking a daemon where its root is confirms the configuration, not the disk. The plan therefore has two limbs, and the primary success check is df -hT /, not anything Docker reports about itself.

Unconfirmed — the per-subdirectory du was blocked (next paragraph). The docker/containerd split is closer to 50/50 than the 28/72 the proxy suggested; the conclusion is unchanged: half the bytes are containerd's, and data-root alone does not move them.

Why the per-subdirectory breakdown didn't work from the grant: sudo -n du -sh /var/lib/docker/* failed with "No such file or directory" for a file literally named *. The directory is 0710, so the unprivileged shell cannot enumerate it; bash passes the unexpanded glob through, and sudo elevates the final command, not the expansion that preceded it. A working breakdown needs root's own shell to expand — a broader grant than a bare du, so it was not added. Your interactive root session has no such problem.

Container writable layers are unusually large (uikit-dev 2.38 GB, entu-research 1.22 GB, backlog-triage 1.02 GB, apex-research 1.03 GB) — the Claude-team containers are accumulating state in their writable layer rather than a volume. Worth a separate look; not blocking here.

Containers, volumes, bind mounts

9 containers, 8 running, 1 stopped (cortex-db, exited 3 weeks ago — pre-existing). 15 named volumes, all under /var/lib/docker/volumes/, referenced by name — they move transparently with data-root.

No bind mount anywhere references /var/lib/docker or /var/lib/containerd by path. Every bind mount points into /home/dev/…, /usr/local/share/ca-certificates/, or /home/docker-data/xireactor/pgdata (cortex-db's Postgres data — already on the /home LV, a working precedent). Moving the roots is invisible to every container's own mount table; nothing on the container side needs reconfiguring.

The three team containers — apex-research :2222, polyphony-dev :2223, entu-research :2224 — all run network_mode: host. Their sshd binds directly to the host; Docker publishes no ports for them. That simplifies the restart and breaks the obvious verification command (see 3.9).

Not determinable from the survey — closed in pre-flight

  • Exact byte size of /var/lib/docker and /var/lib/containerd — measured 16:52: 22 G + 21 G. Their internal breakdown needs an interactive root shell (the glob issue noted above).
  • Whether BuildKit's 3.62 GB cache is Docker- or containerd-managed — either way, it moves with one of the two limbs.
  • LVM free-extent state — measured: VFree 0. The 475 G volume group is fully allocated (home 400 G, root 59 G, swap 16 G). Growing root was never available without shrinking /home first — strictly more invasive than this plan. Changes nothing: the plan uses /home's filesystem headroom, not VG free space.
  • Container restart policies — decides what comes back by itself → checked in pre-flight; see 3.4.

2 Desired outcome — what "done" looks like

  1. Both Docker's data root and containerd's root physically reside on the vg-home LV. Moving only one is an incomplete migration, not a smaller complete one.
  2. docker info reports the new Docker Root Dir and config.toml reports the new root — but the df -hT / delta is what proves the outcome.
  3. All 15 images, 9 containers (identical IDs) and 15 volumes present and functional. Nothing re-pulled, re-cloned or re-created.
  4. All eight running containers reachable and working as before, after one planned restart.
  5. / usage lands around 15%. Measured: 52 G used − 43 G moved = 9 G on 58 G ≈ 15.5% (call it 14–17% for du -sh's whole-gigabyte rounding). Earlier drafts said "~20% at best" from the 40.7 GB proxy; the real total is larger because the proxy omits container logs, so more moves and root lands lower.
  6. The old directories on root are not deleted until success is independently verified and the hold period has passed. Until then they are the rollback path, not scratch space.
  7. No compose file, container config or bind-mount path changes anywhere.

3.1 Why two limbs, not one — read once

Docker and containerd are separate daemons with separately configured storage roots (see the catch). Relocating only Docker's data-root moves the volumes and possibly the build cache, but leaves the image and container layers — a measured 21 G, about half the bytes — on root under /var/lib/containerd. Every Docker-level check would pass. df -hT / would not move. That is why df is the primary pass/fail signal in 3.5.

Mechanism for both: a config-file root relocation — data-root in daemon.json, root in config.toml — rather than a bind mount over the original path. Neither daemon has any systemd customisation to fight, and the bind-mount failure mode (a daemon racing an unmounted directory at boot and silently repopulating an empty one on root) is exactly the silent-divergence class this estate has already been bitten by. Config-file relocation has no such race.

3.2 Copy primitive — rsync -aHAX, never cp

Snapshotter storage depends on hardlinks (layers shared between images, containers and snapshots) and extended attributes (overlayfs whiteout markers for deleted files). cp -r breaks the hardlinks — bloating disk and corrupting shared-layer bookkeeping — and drops the xattrs, so deleted files reappear inside containers that look copied correctly. -a archive, -H hardlinks (the load-bearing flag), -A ACLs, -X xattrs, --numeric-ids keeps raw 0:0 ownership.

3.3 The migration — literal commands, in order

1

Phase 1 — live copy. No downtime yet; both daemons keep running.

sudo mkdir -p /home/docker-data/lib-docker /home/docker-data/lib-containerd
sudo rsync -aHAX --numeric-ids /var/lib/docker/     /home/docker-data/lib-docker/
sudo rsync -aHAX --numeric-ids /var/lib/containerd/ /home/docker-data/lib-containerd/
ExpectedBoth complete with no error output. With 43 G to copy this will take a while — fine, nothing is down. Time it; phase 2 will be a small fraction of this.
StopIf either rsync reports errors, do not stop any service. Re-run the failing rsync (it is safe to re-run and resumes) until it completes clean.

Pre-existing, not migration-caused, fires only on an empty volume — which this migration does not create. apex-research's entrypoint (/entrypoint-apex.sh) has a known crash-loop bug: a git clone step before sshd binds, under set -e, that aborts on a network or auth failure (diagnosed and patched in apex-migration-research PRs #182/#183). It triggers only when the persistent volume is fresh. This migration copies the volumes intact, so the guarded code path should run.

A climbing RestartCount on apex-research alone, with the other seven fine and df having dropped, matches that bug's signature — not a storage problem. Investigate via the logs. Rolling back would not fix an entrypoint bug and would undo a migration that worked.

3.6 Do-not-delete gate — a separate step, on a later day

Run only when every check in 3.5 passed — the df delta specifically — and the hold period you decided in pre-flight has elapsed. Default 24–48 h of normal operation. There is no space pressure: /home holds both copies of both directories comfortably.

sudo rm -rf /var/lib/docker
sudo rm -rf /var/lib/containerd
IrreversibleThis is the only step in the runbook that cannot be undone. Once it has run, 3.7 no longer applies.

3.7 Rollback — run this instead of the gate if verification fails

The old directories are never modified before 3.6, so rollback is near-instant and no data was ever at risk.

sudo systemctl stop docker.service
sudo systemctl stop docker.socket
sudo systemctl stop containerd.service

sudo rm /etc/docker/daemon.json
sudo sed -i 's|^root = "/home/docker-data/lib-containerd"|#root = "/var/lib/containerd"|' /etc/containerd/config.toml
grep -n 'root' /etc/containerd/config.toml

sudo systemctl start containerd.service
sleep 2
sudo systemctl start docker.socket
sudo systemctl start docker.service

docker ps -a
Expectedgrep shows #root = "/var/lib/containerd" commented again; then the original 9 containers with their original IDs, running on the untouched originals.
Always roll back bothEven if only one daemon looked like the problem. Docker on the old root with containerd still pointed at a possibly incomplete new location is a new untested configuration, not a return to known-good.

If a phase 1 or phase 2 rsync itself failed — before you touched either config — there is nothing to roll back. The originals are still authoritative; fix and re-run the rsync.

3.8 Team impact

Downtime

One window: phase 2 delta rsync + both daemon restarts + container restart. The bulk moved live in phase 1, so the outage is drift-only — likely well under 15 minutes. Time your own phase 1 before promising a number to the teams.

Who to tell

  • apex-research · polyphony-dev · entu-research — SSH on 2222/2223/2224 unreachable during the window
  • allerk users
  • anything depending on cortex-mcp (8011) / cortex-api (8010)

Nothing on their side changes. No compose edits, no path changes.

3.9 Why network_mode: host cuts both ways

  • Simpler restart. Bridge-networked containers need their virtual bridge, veth pairs and iptables DNAT rules torn down and rebuilt across a daemon restart. These three have none of that — sshd binds straight to the host NIC the moment the container process starts.
  • Broken obvious check. docker port is empty for them by design, healthy or not. 3.5 uses ss -tlnp plus a real SSH probe instead.
  • No sidecar to sequence. None run a cloudflared or reverse-proxy sidecar, so a clean SSH probe on the bound port is a complete functional check by itself.
