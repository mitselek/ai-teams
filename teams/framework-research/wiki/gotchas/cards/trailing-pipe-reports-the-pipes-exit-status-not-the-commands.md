## TLDR

`cmd | tail` reports **`tail`'s** exit status, and `tail` almost always succeeds -- so any `RUN`, `rc=$?`, or CI step ending in a pipe **reports success for a failed command.** Fix: `cmd; rc=$?` **before** any pipe, or `set -o pipefail`. **Better -- assert the outcome:** `RUN test -x ~/.local/bin/claude && claude --version`.

## Key ideas

- **THE DURABLE HALF -- this was DECLINED three hours earlier and the decline was reversed by a third instance.** The rule was *silent-wrong earns an entry, visible-wrong is a shell fact*; instance 1 looked visible-wrong (`rc=0` printed **directly beneath** `curl: (28)`). **The reversal shows the criterion was applied to the wrong consumer.** → ***Visibility is relative to whoever CONSUMES the signal, not to whoever reads the log.***
- **Instance 1 (bridge probe):** consumer is a **human reading a log** with both lines adjacent -- visible-wrong, cost a misleading annotation.
- **Instance 3 (Dockerfile):** `RUN curl --insecure ... | bash 2>&1 | tail -5` **printed a TLS cert error and reported `DONE 0.6s`.** Consumer is the **build system, which reads only the exit status** -- for it the failure is **completely invisible.** Cost: **a green build that shipped an image with no `claude` in it**, the container's primary tool, with nothing reporting a problem. **Same mechanism, classification flips entirely on who is reading.**
- **Second, compounding defect in the same line: `--insecure` applies to the OUTER transfer only** -- it does not reach the `curl` calls *inside* the script you piped into `bash`. The inner fetch hits TLS interception with default verification and fails. **The two defects mask each other: the inner failure is real, and the trailing pipe hides that it happened.** Either alone would likely have been caught.
- **Remedy in strength order:** (1) **assert the outcome, not the status** (`test -x <path> && <tool> --version`) -- catches it regardless of how the status was mangled *and* regardless of which defect caused it; `daemon-self-report-confirms-config-not-outcome` at the build layer, since **a layer's status is not the image's contents**; (2) `set -o pipefail` **at both levels** when a script is piped into a shell; (3) drop the trailing pipe -- `| tail` buys a shorter log and costs the exit status, a bad trade in any gating context.
- **Correlation flagged:** two evidenced instances, one author, one day. Mechanism is unaffected (a shell fact, checkable by inspection) but the **frequency claim rests on one vantage**; path = a second author or repo.
- **[PATH NOT WALKED -- and this card first said it was. Corrected same day on the submitter's insistence.]** Instances 4 and 5 are `Dockerfile.apex` layers #16 and #10, in a build the team ran: #16 printed a TLS verification failure and reported **`DONE 0.8s`**, binary **absent from the resulting image**; #10's `npm install -g npm@latest` printed `npm error` and reported **`DONE 19.0s`**. **The first version of this note claimed they discharged the correlation flag "on both counts at once", asserting the file was authored outside the team. FALSE -- both apex lines are Brunel's.** A second REPO but the SAME author. **And the correlation is worse than the flag supposed: the apex line PREDATES the joosep one, so instance 3 was almost certainly copied from instance 4** -- evidence of **one author propagating one bad line across repos**, i.e. propagation, not independent frequency. **The flag stands OPEN; what discharges it is an instance in an artifact Brunel did not write.** Left visible rather than overwritten, at the submitter's request (*"please do not let me weaken it"*): **an over-generous reading of a correlation flag, committed by the person maintaining it.**
- **[WHAT SURVIVES, independent of authorship] Instance 5 BREAKS THE IDIOM.** Every prior instance is `curl ... | bash`; this is a different command entirely, **relocating the trap to the trailing pipe rather than the piped-installer pattern.** It is also **the variant most likely to be left in place** -- small blast radius (only npm's self-upgrade lost, Node fine), so a reader shrugs it off.
- **[DIAGNOSIS UPGRADED -- "not flaky, impossible"] OBSERVED: the WARP CA file does not exist in the image at all** (the entrypoint installs it only `if [ -f ]` at container START, where it is a bind-mount). **So no CA exists at any point during any build: that layer NEVER HAD A ROUTE TO SUCCEED. Not a flaky install -- an install that could not work, reporting success, for ~six weeks.** Moves the account of the second defect from *the flag did not propagate* to **the prerequisite was never present** -- the first reading invites the wrong fix. **INFERRED, NOT PROVEN and kept separate:** the outer `curl` has `--insecure` so is not the failing fetch; the failure is most likely `install.sh`'s own inner download.
- **[REMEDY CORRECTION] `set -o pipefail` is UNAVAILABLE where this bites.** A Dockerfile `RUN` runs under `/bin/sh` = **dash** on Debian/Ubuntu bases, which has no `pipefail`; using it needs a `SHELL` change first. **So the outcome assertion is not merely strongest, it is the ONLY one of the three that works there** -- the existing ordering is load-bearing, not a preference.
- **[REMEDY 1 CONFIRMED IN PRACTICE, same day]** `&& [ "$(claude --version | cut -d' ' -f1)" = "${CLAUDE_VERSION}" ]` went into the base `Dockerfile`; **the assertion ran inside the build and passed**, and the image then gated clean against a rollback control. Note the form: **exact field compare, not `grep -qF`, because a shorter version pin satisfies a `grep -qF` as a PREFIX.**
- **[DEFERRED FIX -- DELETE, DO NOT REPAIR] `Dockerfile.apex` carries both masked layers and no assertion on any layer.** **Both should be DELETED, not fixed:** a *working* native install would hand apex **a second `claude` binary the login PATH silently prefers** -- the exact failure this session spent a morning ruling out; and the npm self-upgrade **wants a newer Node than apex pins, so it can only ever fail.** **Both deletions are subtractive, which is what makes them safe.** Apex repo: own PR, own build, own recreate. Deferred at the submitter's call.
